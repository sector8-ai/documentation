---
title: Onboarding
description: Get a new Sector8 customer from runtime credentials to a verified evaluate-before-dispatch proof.
---

Connect your application to Sector8 with the credentials issued to your environment, prove both an `ALLOW` path and a known `DENY` path, and confirm your runtime honors both before you write more code.

Telemetry can follow later. Telemetry or health alone is not onboarding success.

## What you need

- The Sector8 runtime credentials issued to your environment (`SECTOR8_API_KEY` and `SECTOR8_CLIENT_ID`)
- Python 3.10+, Node.js 18+, or a runtime that can call `POST /api/v1/evaluate`
- Access to the application path where you can allow dispatch, block on `DENY`, and fail closed on errors

<Info>
Use the credentials issued to your environment. Contact [support@sector8.ai](mailto:support@sector8.ai) or [book a demo](https://sector8.ai/contact) if you do not have them yet.
</Info>

Public docs use the production host `https://sdkapi.sector8.ai`. Use the endpoint and credentials issued to your environment.

## Recommended first run

<Steps>
  <Step title="Set your credentials">
    Inject the credentials issued to your environment through env vars. Do not generate, share, or commit runtime keys in source control.

    ```bash
    export SECTOR8_BASE_URL="https://sdkapi.sector8.ai"
    export SECTOR8_API_KEY="YOUR_API_KEY"
    export SECTOR8_CLIENT_ID="YOUR_CLIENT_ID"
    ```
  </Step>

  <Step title="Confirm the gate is reachable">
    ```bash
    curl -s "$SECTOR8_BASE_URL/api/health"
    ```

    If health fails, do not route live actions until the endpoint is reachable.
  </Step>

  <Step title="Pick one evaluate path">
    Use one of these guides and call `evaluate` before dispatch:

    - [Quickstart](/guides/quickstart)
    - [Python SDK](/guides/python-sdk)
    - [TypeScript SDK](/guides/typescript-sdk)
    - [Non-MCP integration](/guides/non-mcp-integration)
    - [Guard MCP Server](/guides/mcp-server)
  </Step>

  <Step title="Prove ALLOW and DENY">
    Run two evaluate-before-dispatch proofs on the same integration path:

    1. A safe proposed action that returns `ALLOW`, then dispatch only in that branch
    2. A known unsafe or policy-blocked action that returns `DENY`, and confirm it never executes

    Honor every decision the same way:

    | Result | Runtime must |
    | --- | --- |
    | `ALLOW` | May dispatch |
    | `DENY` | Block; do not dispatch |
    | `REVIEW` | Pause / route to approval; do not dispatch |
    | Missing, unknown, error, or timeout | Fail closed; do not dispatch |

    Sector8 returns the verdict. Your application owns enforcing it at the dispatch boundary.
  </Step>

  <Step title="Verify the result">
    Confirm:

    - health responds for your environment
    - the `ALLOW` path returned a decision artifact and your app dispatched only then
    - the `DENY` path returned a decision artifact and your app blocked execution
    - `REVIEW` / unknown / error paths do not execute
    - both decision artifacts include `reason_code`, `decision_trace_id`, `evidence_hash`, and `policy_version_id`
  </Step>
</Steps>

<Check>
You are onboarded when both an `ALLOW` path and a known `DENY` path are proven against the credentials and endpoint issued to your environment, and your application honors both at dispatch.
</Check>

## Common mistakes

<Warning>
Use `https://sdkapi.sector8.ai` for public production examples. Do not paste real runtime keys into docs, tickets, chat, or source control.
</Warning>

- Treating connection health, telemetry, or a single `ALLOW` as full onboarding proof
- Skipping a known unsafe or policy-blocked `DENY` proof
- Logging an LLM event without calling `evaluate` before tool dispatch
- Treating `REVIEW` as a generic deny instead of an approval pause
- Hardcoding `SECTOR8_API_KEY` or `SECTOR8_CLIENT_ID` in source
- Forgetting a stable `session_id` on governed tool calls
- Assuming unconnected tool paths are covered automatically
