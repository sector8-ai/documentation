This is the **only Start-here linear path**. Complete every step below with published packages and credentials issued to you. Do not treat health checks, telemetry, or a single `ALLOW` as onboarding success.

**You will:**

1. Install and authenticate  
2. Produce expected `ALLOW` and `DENY`  
3. Retrieve matching decision evidence  
4. Verify observation continues on `DENY` / evaluation failure  
5. Verify enforcement dispatches only on `ALLOW`

Latency budgets and concurrency limits are **out of scope** for this journey. Completing onboarding does not certify pilot kickoff performance.

## What you need

- Runtime credentials issued by Sector8 Operator / support (`SECTOR8_API_KEY`, `SECTOR8_CLIENT_ID`) — **shell env or local env file only**. Never paste keys into chat, tickets, or source control.
- Separately provisioned **dashboard** access (browser session) for Decision Feed. The runtime key is **not** authority for dashboard APIs.
- Python 3.10+ **or** Node.js 18+
- For the refund walkthrough: a **pinned** checkout of the SDK examples (npm/pip do not ship `examples/`)

<Info>
No credentials yet? Contact [support@sector8.ai](mailto:support@sector8.ai) or [book a demo](https://sector8.ai/contact). Do not borrow another tenant’s key.
</Info>

## Environment variables (do not mix names)

| Interface | Endpoint variable | Staging example |
| --- | --- | --- |
| Python SDK / `sector8-verify` | `SECTOR8_ENDPOINT` | `https://stgsdkapi.sector8.ai` plus `SECTOR8_UNSAFE_ENDPOINT=true` |
| TypeScript SDK / many curl samples | `SECTOR8_BASE_URL` | `https://stgsdkapi.sector8.ai` |
| Production default (public docs) | (SDK default) | `https://sdkapi.sector8.ai` |

These names are **not interchangeable** across tools. Set the name your installed interface documents.

## Journey

<Steps>
  <Step title="1. Set credentials securely">
    Inject issued credentials through your shell or a local `.env` that is gitignored.

    **Python verifier / client:**

    ```bash
    export SECTOR8_API_KEY="YOUR_API_KEY"
    export SECTOR8_CLIENT_ID="YOUR_CLIENT_ID"
    export SECTOR8_ENDPOINT="https://stgsdkapi.sector8.ai"   # staging
    export SECTOR8_UNSAFE_ENDPOINT=true
    ```

    **TypeScript client / REST samples:**

    ```bash
    export SECTOR8_API_KEY="YOUR_API_KEY"
    export SECTOR8_CLIENT_ID="YOUR_CLIENT_ID"
    export SECTOR8_BASE_URL="https://stgsdkapi.sector8.ai"   # staging
    ```
  </Step>

  <Step title="2. Install published packages (pinned)">
    **Python**

    ```bash
    python -m venv .venv
    source .venv/bin/activate   # Windows: .venv\Scripts\activate
    pip install sector8-sdk==1.0.4
    sector8-verify --help
    ```

    **TypeScript**

    ```bash
    mkdir s8-onboard && cd s8-onboard
    npm init -y
    npm install @sector8/sdk@1.0.4
    ```
  </Step>

  <Step title="3. Confirm the gate is reachable">
    ```bash
    curl -s https://stgsdkapi.sector8.ai/api/health
    # or production:
    curl -s https://sdkapi.sector8.ai/api/health
    ```

    If health fails, stop. Do not route live actions.
  </Step>

  <Step title="4. Prove ALLOW and DENY (evaluation-only verifier)">
    The built-in verifier proves the evaluate contract. It is **evaluation-only** — it does not know your dispatch mode.

    **Python**

    ```bash
    sector8-verify
    ```

    Expect lines like `ALLOW verified. Trace: …` and `DENY verified. Trace: …`. Record both trace IDs.

    **TypeScript** — use the SDK evaluate helpers or copy `examples/onboarding-verify.js` from a [pinned TypeScript SDK tag](https://github.com/sector8-ai/sector8-sdk-typescript) after `npm install @sector8/sdk@1.0.4`.

    <Warning>
    Evaluate timeouts that are too aggressive can fail-close safe traffic. Prefer the SDK defaults unless your Operator gives a specific timeout for your path. This page does **not** define a product latency budget.
    </Warning>
  </Step>

  <Step title="5. Retrieve matching evidence">
    1. Open your staging (or issued) dashboard and go to **Decisions**.
    2. Use **Verify** / lookup with each `decision_trace_id` from step 4.
    3. Confirm matching `outcome`, `reason_code`, `policy_version_id`, and `evidence_hash`.

    Dashboard login is a **session cookie**. Do not send the runtime API key to dashboard APIs.
  </Step>

  <Step title="6. Observe and enforce proofs (refund walkthrough)">
    Examples are **not** inside the npm/pip package. Clone or download at a pinned commit/tag:

    - Python: [sector8-sdk-python examples/PILOT.md](https://github.com/sector8-ai/sector8-sdk-python/blob/main/examples/PILOT.md)
    - TypeScript: [sector8-sdk-typescript examples/PILOT.md](https://github.com/sector8-ai/sector8-sdk-typescript/blob/main/examples/PILOT.md)

    Offline (no credentials) — proves helper dispatch effects only:

    ```bash
    # Python
    python examples/refund_pilot_walkthrough.py --offline

    # TypeScript (from that repo after npm install)
    npm run refund-pilot:offline
    ```

    Live staging (Operator-issued key + Refund Agent fixture bound for your tenant):

    ```bash
    # Python
    python examples/refund_pilot_walkthrough.py

    # TypeScript
    npx ts-node --transpile-only examples/refund-pilot-walkthrough.ts
    ```

    Fixture defaults (confirm with Operator): cap **100 GBP**, under **25**, over **250**, agent `Refund Agent`, expect over-cap `DENY` / `AMOUNT_LIMIT_EXCEEDED`.

    | Mode | What must be true |
    | --- | --- |
    | **Enforce** | Valid `ALLOW` → exactly one **fake** refund dispatch; `DENY` / timeout / auth / malformed → **zero** dispatches |
    | **Observe** | Workflow **continues** once even on `DENY` or evaluation failure; report `decision` separately from `dispatched` |

    Fake refunds never move money. Wrong fixture binding is a **mismatch**, not success. Copy live `decision_trace_id` values back into Decision Feed Verify.
  </Step>

  <Step title="7. Completion checklist">
    - [ ] Published `1.0.4` packages installed in a clean environment  
    - [ ] Credentials only via shell / local env file  
    - [ ] Verifier (or equivalent) produced `ALLOW` + `DENY` with artifact fields  
    - [ ] Both traces retrieved in Decision Feed and fields matched  
    - [ ] Observe proof: continuation on DENY / failure  
    - [ ] Enforce proof: dispatch only on ALLOW  
    - [ ] No founder undocumented steps required  

    You are onboarded when this checklist is complete for your language path.
  </Step>
</Steps>

## Common mistakes

- Mixing `SECTOR8_ENDPOINT` and `SECTOR8_BASE_URL` across tools  
- Pasting runtime keys into chat or committing them  
- Using the runtime key against dashboard APIs  
- Treating `--offline` helper proofs as live gate evidence  
- Claiming observation “had zero impact” on a real production workflow  
- Branching only on `reason_code` instead of `outcome` / `decision` for enforce
