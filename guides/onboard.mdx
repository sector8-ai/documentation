This is the **only Start-here linear path**. Complete every step below with published packages and credentials issued to you. Do not treat health checks, telemetry, or a single `ALLOW` as onboarding success.

**You will:**

1. Install and authenticate  
2. Produce expected `ALLOW` and `DENY`  
3. Retrieve matching decision evidence  
4. Verify observation continues on `DENY` / evaluation failure  
5. Verify enforcement dispatches only on `ALLOW`

Latency budgets and concurrency limits are **out of scope** for this journey. Completing onboarding does not certify pilot kickoff performance.

## What you need

- Runtime credentials issued by Sector8 Operator / support (`SECTOR8_API_KEY`, `SECTOR8_CLIENT_ID`) — **shell env or local env file only**. Never paste keys into chat, tickets, or source control.
- Separately provisioned **dashboard** access (browser session) for Decision Feed. The runtime key is **not** authority for dashboard APIs.
- Python 3.10+ **or** Node.js 18+
- Example scripts downloaded at the **immutable SHAs** below (npm/pip do not ship `examples/`)

<Info>
No credentials yet? Contact [support@sector8.ai](mailto:support@sector8.ai) or [book a demo](https://sector8.ai/contact). Do not borrow another tenant’s key.
</Info>

## Environment variables

Both example scripts accept **either** `SECTOR8_ENDPOINT` **or** `SECTOR8_BASE_URL` (same host). Staging always requires the unsafe opt-in:

| Variable | Required when |
| --- | --- |
| `SECTOR8_API_KEY` | Always for live runs |
| `SECTOR8_CLIENT_ID` | Always for live runs |
| `SECTOR8_ENDPOINT` or `SECTOR8_BASE_URL` | Staging: `https://stgsdkapi.sector8.ai` |
| `SECTOR8_UNSAFE_ENDPOINT=true` | Any non-default host (including staging) for **both** language paths |

```bash
# bash
export SECTOR8_API_KEY="YOUR_API_KEY"
export SECTOR8_CLIENT_ID="YOUR_CLIENT_ID"
export SECTOR8_ENDPOINT="https://stgsdkapi.sector8.ai"
export SECTOR8_UNSAFE_ENDPOINT=true
```

```powershell
# PowerShell
$env:SECTOR8_API_KEY = "YOUR_API_KEY"
$env:SECTOR8_CLIENT_ID = "YOUR_CLIENT_ID"
$env:SECTOR8_ENDPOINT = "https://stgsdkapi.sector8.ai"
$env:SECTOR8_UNSAFE_ENDPOINT = "true"
```

Local `.env` files are fine if gitignored. Neither walkthrough auto-loads dotenv — export vars in the shell (or `Get-Content .env` patterns you already use) before running.

## Journey

<Steps>
  <Step title="1. Set credentials securely">
    Inject issued credentials through your shell (bash or PowerShell above). Never paste keys into chat.
  </Step>

  <Step title="2. Install published packages (pinned)">
    **Python**

    ```bash
    python -m venv .venv
    source .venv/bin/activate   # Windows: .venv\Scripts\Activate.ps1
    pip install sector8-sdk==1.0.4
    ```

    **TypeScript**

    ```bash
    mkdir s8-onboard && cd s8-onboard
    npm init -y
    npm install @sector8/sdk@1.0.4
    ```
  </Step>

  <Step title="3. Download example scripts at the pinned SHA">
    **TypeScript (bash)**

    ```bash
    SHA=3aa27b4
    curl -fsSL -o onboarding-verify.js \
      "https://raw.githubusercontent.com/sector8-ai/sector8-sdk-typescript/$SHA/examples/standalone/onboarding-verify.js"
    curl -fsSL -o refund-pilot-core.js \
      "https://raw.githubusercontent.com/sector8-ai/sector8-sdk-typescript/$SHA/examples/standalone/refund-pilot-core.js"
    curl -fsSL -o refund-pilot-walkthrough.js \
      "https://raw.githubusercontent.com/sector8-ai/sector8-sdk-typescript/$SHA/examples/standalone/refund-pilot-walkthrough.js"
    ```

    **TypeScript (PowerShell)**

    ```powershell
    $SHA = "3aa27b4"

      "https://raw.githubusercontent.com/sector8-ai/sector8-sdk-typescript/$SHA/examples/standalone/onboarding-verify.js"

      "https://raw.githubusercontent.com/sector8-ai/sector8-sdk-typescript/$SHA/examples/standalone/refund-pilot-core.js"
    ```

    **Python (bash)**


    **Python (PowerShell)**

    ```powershell

      "https://raw.githubusercontent.com/sector8-ai/sector8-sdk-python/$SHA/examples/onboarding_verify.py"

    ```
  </Step>

  <Step title="4. Confirm the gate is reachable">
    ```bash
    curl -s https://stgsdkapi.sector8.ai/api/health
    # or production:
    curl -s https://sdkapi.sector8.ai/api/health
    ```

    If health fails, stop. Do not route live actions.
  </Step>

  <Step title="5. Prove ALLOW and DENY (full artifact fields)">
    Use the downloaded verifiers — they print `outcome`, `reason_code`, `decision_trace_id`, `evidence_hash`, and `policy_version_id` for Decision Feed comparison.

    **Python**

    ```bash
    python onboarding_verify.py
    ```

    **TypeScript**

    ```bash
    node onboarding-verify.js
    ```

    These scripts import the **published** packages only (`sector8-sdk` / `@sector8/sdk`). They do not require a repository `dist/` or `src/` tree.

    <Info>
    The package CLI `sector8-verify` still prints traces only. Prefer `onboarding_verify.py` / `onboarding-verify.js` for full-field proof.
    </Info>

    <Warning>
    Evaluate timeouts that are too aggressive can fail-close safe traffic. Prefer the SDK defaults unless your Operator gives a specific timeout for your path. This page does **not** define a product latency budget.
    </Warning>
  </Step>

  <Step title="6. Retrieve matching evidence">
    1. Open your staging (or issued) dashboard and go to **Decisions**.
    2. Use **Verify** / lookup with each `decision_trace_id` from step 5.
    3. Confirm matching `outcome`, `reason_code`, `policy_version_id`, and `evidence_hash` against the JSON printed by the verifier.

    Dashboard login is a **session cookie**. Do not send the runtime API key to dashboard APIs.
  </Step>

  <Step title="7. Observe and enforce proofs (refund walkthrough)">
    Offline (no credentials) — proves helper dispatch effects only. Simulated trace IDs have **no** Decision Feed row — do not look them up.

    ```bash
    # Python
    python refund_pilot_walkthrough.py --offline

    # TypeScript
    node refund-pilot-walkthrough.js --offline
    ```

    Live staging (Operator-issued key + Refund Agent fixture bound for your tenant):

    ```bash
    # Python
    python refund_pilot_walkthrough.py

    # TypeScript
    node refund-pilot-walkthrough.js
    ```

    Fixture defaults (confirm with Operator): cap **100 GBP**, under **25**, over **250**, agent `Refund Agent`, expect over-cap `DENY` / `AMOUNT_LIMIT_EXCEEDED`.

    | Mode | What must be true |
    | --- | --- |
    | **Enforce** | Valid `ALLOW` → exactly one **fake** refund dispatch; `DENY` / timeout / auth / malformed → **zero** dispatches |
    | **Observe** | Workflow **continues** once even on `DENY` or evaluation failure; report `decision` separately from `dispatched` |

    Live mode **fails closed** when expected outcomes are missing (network failure, wrong verdict, or wrong reason). Fake refunds never move money. Wrong fixture binding is a **mismatch**, not success. Copy **LIVE** `decision_trace_id` values back into Decision Feed Verify.
  </Step>

  <Step title="8. Completion checklist">
    - [ ] Published `1.0.4` packages installed in a clean environment  
    - [ ] Example files downloaded at the immutable SHAs above (no local edits)  
    - [ ] Credentials only via shell / local env file  
    - [ ] Verifier produced `ALLOW` + `DENY` with full artifact fields  
    - [ ] Both traces retrieved in Decision Feed and fields matched  
    - [ ] Observe proof: continuation on DENY / failure  
    - [ ] Enforce proof: dispatch only on ALLOW  
    - [ ] No founder undocumented steps required  

    You are onboarded when this checklist is complete for your language path.
  </Step>
</Steps>

## Common mistakes

- Omitting `SECTOR8_UNSAFE_ENDPOINT=true` for staging on TypeScript or Python examples  
- Pasting runtime keys into chat or committing them  
- Using the runtime key against dashboard APIs  
- Treating `--offline` helper proofs as live gate evidence  
- Looking up simulated trace IDs in Decision Feed  
- Cloning `main` instead of the immutable SHA for examples  
- Claiming observation “had zero impact” on a real production workflow  
- Branching only on `reason_code` instead of `outcome` / `decision` for enforce
